# Ручная приёмка multi-device sync

## Подготовка

1. Запустить общий локальный PostgreSQL и Serverpod на `http://localhost:8083/`.
2. Запустить Windows Flutter с `CM_SERVER_URL=http://localhost:8083/`.
3. Подключить Android-устройство и создать туннель:

```powershell
adb reverse tcp:8083 tcp:8083
```

4. Запустить Android Flutter с `CM_SERVER_URL=http://localhost:8083/`.
5. Войти на обоих клиентах в один аккаунт.
6. Для автоматического pull держать приложения в foreground. Интервал polling — 12 секунд; локальные изменения запускают sync сразу.

Перед каждым сценарием дождаться статуса без pending-операций. Сравнивать не только список, но и открытый лист персонажа после одного интервала polling.

## Сценарии

### 1. Windows -> Android

1. На Windows изменить HP или другое поле существующего персонажа.
2. Не нажимать дополнительных кнопок синхронизации.
3. На Android дождаться автоматического обновления.

Ожидание: новое значение появляется один раз, Android не остаётся в состоянии ожидания синхронизации.

### 2. Android -> Windows

1. На Android изменить заметку.
2. На Windows оставить открытым список или лист этого персонажа.
3. Дождаться polling.

Ожидание: Windows показывает заметку без повторного входа в персонажа.

### 3. Независимые offline-изменения

1. Отключить Android-туннель:

```powershell
adb reverse --remove tcp:8083
```

2. На Android изменить заметку или AC bonus.
3. На Windows изменить другое поле того же персонажа.
4. Восстановить туннель:

```powershell
adb reverse tcp:8083 tcp:8083
```

5. Дождаться retry и polling на обоих клиентах.

Ожидание: сохраняются оба независимых изменения, состояния сервера, Android и Windows совпадают.

### 4. Same-target conflict

1. Отключить Android-туннель.
2. Задать разные значения одного поля, например имени, на Android и Windows.
3. Дать Windows синхронизироваться, затем восстановить туннель.

Ожидание: серверное canonical-значение побеждает; Android принимает его, rejected operation больше не повторяется.

### 5. Semantic action против barrier

1. Отключить Android-туннель.
2. На Android потратить HP, spell slot или feature resource semantic action.
3. На Windows выполнить rest, который меняет barrier соответствующего ресурса.
4. Восстановить туннель.

Ожидание: устаревшее действие отклоняется как `crossed_barrier`, оба клиента принимают canonical server state.

### 6. Offline create

1. Отключить Android-туннель и создать персонажа.
2. Несколько раз отредактировать его до reconnect.
3. Восстановить туннель и дождаться синхронизации на обоих клиентах.

Ожидание: на сервере и Windows ровно один персонаж; отрицательный local id исчезает после remap.

### 7. Remote delete

1. Удалить персонажа на Windows.
2. Дождаться Android polling.

Ожидание: персонаж исчезает на Android вместе с локальными stale operations и не воскрешается.

### 8. Quick edit + Back

1. Изменить текстовое поле на каждом клиенте и сразу вернуться назад.
2. Повторно открыть персонажа.
3. Дождаться синхронизации на втором клиенте.

Ожидание: последнее принятое UI-значение сохранено локально и приходит на второй клиент.

### 9. Android force close с pending

1. Отключить Android-туннель и изменить персонажа.
2. Принудительно закрыть приложение.
3. Запустить его снова, восстановить туннель и войти тем же аккаунтом.

Ожидание: SQLite восстанавливает pending operation, retry завершается без клона и без вечного dirty.

### 10. Длительное чередование

Несколько минут поочерёдно менять разные поля и выполнять semantic actions на обоих клиентах, периодически отключая Android-туннель.

Финальное ожидание после стабилизации сети и опустошения очередей:

```text
server persisted mutable state
== Android persisted mutable state
== Windows persisted mutable state
```

Недопустимы клоны, stale rollback, permanent dirty, endless retry и пропущенные remote updates.
